# R05 — activate the private preset guard patch (`20261027090000`)

**Status: prepared and rehearsed only. Nothing has been run on any hosted database.**
Run only in the serialized slot the release coordinator assigns. Record target, time and operator in the
private ops log, not in this public repository.

## What remains and why

PR #246 (main `73bdf619`, live) lets the app save two more report controls in private presets:
the selected promotion `promo_id` on `/laporan/promo`, and the historical valuation report
`/laporan/nilai-persediaan/historis` with its as-of `tanggal`. The database guard still refuses both, so
those two saves fail with "Hasil penyimpanan belum dapat dikonfirmasi". Every other preset works today.

The only remaining database step is migration
`supabase/migrations/20261027090000_private_report_promo_history_presets.sql`. It replaces the body of
`public.guard_private_report_preset()` (trigger function on `public.private_report_presets`) by exact text
substitution: one path added to the allowed list, two report-specific keys allowed on their own report only.
It does **not** touch any table, row, RLS policy, grant, role or credential.

## Procedure

1. Run `01`. Every row with an expected value must show `ok = true`; last row `SUMMARY | 0 failed`.
   It proves: prerequisite `20261026000345` recorded, `20261027090000` not recorded, the guard is exactly the
   repository pre-image (md5 `2af62273edc72a46899471ccb7c0edfb` on PostgreSQL 17.6), both anchors occur once,
   the dry-run patch gives exactly the post-image (md5 `a638bdea4dfe40865e312257f3936f56`), and trigger, grants,
   RLS and policy are as expected. **Any failed row: stop**, nothing has been changed.
2. Run `02` once. Success = no error. It takes a brief lock to replace one function (`lock_timeout 5s`,
   `statement_timeout 60s`). Any error aborts the whole transaction; nothing is half-applied. Error codes:
   `R05_ACTIVATION_ALREADY_RECORDED` (already applied, go to step 3), `R05_ACTIVATION_PREIMAGE_MISMATCH`
   (guard drifted since preflight, stop), `R05_PRIVATE_PRESET_GUARD_DRIFT` / `R05_PRIVATE_PRESET_VALIDATION_DRIFT`
   (migration's own guards, stop), `R05_ACTIVATION_POSTIMAGE_MISMATCH` (unexpected result, rolled back, stop),
   lock timeout (retry later).
3. Run `03`: `SUMMARY | 0 failed`.
4. Optional signed-in smoke check by an authorized report user: save a preset on `/laporan/promo` with a promo
   selected; it appears under "Konfigurasi laporan tersimpan" and reopens with the same promo. This is a normal
   user write, not part of the migration.

## Backup: precaution versus what is actually needed

- **No table data is changed**, so no data backup or restore point is needed for this step and there is no
  reason to wait for a fresh full backup. The usual platform backups remain a general precaution only.
- **Minimal pre-image needed: the guard function definition.** Step 1 proves it equals the repository
  pre-image by fingerprint; `04` rebuilds that exact text by reverse substitution and verifies the fingerprint
  before committing. Optional precaution: before step 2, save the output of
  `select pg_get_functiondef('public.guard_private_report_preset()'::regprocedure);` in the private ops log
  (repository code, no customer data).

## Rollback and recovery (only if decided)

`04` refuses unless the guard is exactly the post-image and the history row exists, restores the exact
pre-image, verifies it, and deletes the history row — in one transaction. **No preset row is read, changed or
deleted.** Presets saved or edited after activation remain readable and openable. Until re-activation, the old
guard refuses saving or editing a preset that uses `promo_id` or the historical report (deleting still works).
Re-activation after a rollback is the same steps 1–3 (`01` passes again; the info row then counts those presets).
