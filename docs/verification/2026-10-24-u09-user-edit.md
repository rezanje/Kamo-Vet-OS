## Design and release boundary

- Existing user list gains Aksi/Edit links with account-specific IDs and manager/target restrictions. New editor loads the existing target through current authenticated access, prefilled name/role/branches and opaque version. Self edits retain role/branches. Existing inactive/unavailable assignments remain explicit rather than silently dropped; new choices are active permitted branches.
- One atomic `edit_user_account` RPC replaces no Auth user and calls no signup/configure-existing endpoint. It verifies active current OWNER/ADMIN and existing pengaturan module rules; ADMIN cannot edit privileged peers/OWNER, grant roles beyond either its all_branches or create_accounts capability, or operate outside its current branch permissions. Self role/branch changes and last active manager removal are rejected. There is no new global OWNER expansion or existing policy/capability change.
- Version covers current account fields, assignment roles and HRIS linkage. Grant changes preserve existing PRIMARY/SECONDARY records and add new SECONDARY rows. Per-manager request UUID and payload identity support lost-response retry without duplicate writes; stale or changed requests fail before mutation. Account name changes do not rename HRIS, reassign employment, activate users or rewrite historical operational attribution.
- Append-only `user_account_edits` stores server actor/time, role/branch before-after, name_changed and request/version evidence. It stores no full names, email, password or HRIS payload. Readers need the same current manager/target authority; app INSERT/UPDATE/DELETE are revoked. Existing A01 profile/grant metadata auditing remains unchanged. The editor shows the last 10 records, honestly warning on failed reads.
- Migration `20261024033000_user_account_edit.sql` adds only guarded routines and the new immutable audit table. New execution/select grants are strictly checked and narrower than existing admin profile/grant policies; installing it changes no actual user's rights, capabilities or account data. It does not materially expand persistent access. Schema must precede application deployment. No global RLS changes.
