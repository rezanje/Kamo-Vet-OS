## Scope and behavior

- Named configurations now persist on the server for the authenticated account, including allowed applied filters and selected columns. Another browser using the same account reads the same list. Individual-row save/delete prevents one stale browser from replacing another browser's whole list. Exact-ID retries upsert the same configuration, including when a response is lost. A visible reload control refreshes the list; no realtime/scheduling/sharing mechanism.
- Filter semantics from the prior candidate remain: server-rendered defaults are authoritative, unsent dirty DOM edits are excluded, repeated branches remain repeated, current date/month and doctor/search/detail controls reopen through the original report route. Pagination, acknowledgement/mutation fields, tokens and unapproved destinations are excluded. Changing month through supported GET forms retains applied column choices.
- Existing browser-only records are read only under that account's versioned key and offered for explicit copying. They are never silently uploaded, deleted or used as a fallback after a server failure. Browser-storage failure does not prevent server configurations. A failed/unverifiable server read does not claim an empty list; uncertain save/delete responses show an explanation and retain displayed context.
- Shared report wrappers on allowlisted `/laporan` paths with displayed-data export support native keyboard column controls. Stable header fingerprints plus duplicate occurrence identify tables without storing report rows. Body/footer/empty-row colSpans adapt to visible columns; displayed CSV/Excel and print reflect the chosen columns. Summary values and all report calculations remain unchanged.
- Malformed, duplicate, stale, out-of-range or all-hidden selections show a warning and full table data. Navigation and same-URL server refresh restore the previous owned DOM before applying fresh choices. Choices are bounded to 20 tables, 100 column indices/table, 3,000 JSON characters; configurations remain bounded to 50/account.

## Private storage and existing access

One additive migration: `20261023154500_private_report_presets.sql`. Table stores UUID, server-derived user, name, approved relative report URL and server time. It stores no report rows or new clinical/financial payload. No service credential/client is used.

Owner-only forced RLS applies to SELECT/INSERT/UPDATE/DELETE, with active-profile and existing report-module defaults/custom overrides equivalent to `akses.ts`. There is **no OWNER/ADMIN exception to private ownership**. The feature adds access only to one's own new preference rows; no existing auth, report, branch or role policy is changed. Server actions independently check current session/profile/module and scope reads/deletes to the current user. Client account identity is only a stale-session precondition, never the authoritative owner. Forged owner/time fields are ignored or denied. Opening a stored destination still runs its normal granular report/module/branch checks; storing a link grants no report access.

Database guard bounds report paths/query keys, derives time, prevents owner/ID reparenting and serializes each owner's 50-row quota. An exact existing-ID upsert still works at the limit. Internal trigger execution is revoked from app roles. Global report data/audit payload is not copied into preference rows.
