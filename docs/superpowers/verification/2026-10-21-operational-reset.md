# Recoverable all-branch operational reset

Local implementation passed independent specification and quality review. Quality review independently reran the full reset/restore integration suite. No live reset is evidenced here.

Confirmed scope: every branch, all operational history including examination and inpatient records. Preserve accounts, COA, items, customers/pets, suppliers, employees and settings. An explicit registry currently contains 133 operational tables to clear and 65 master/configuration/audit tables to retain. Unknown tables block maintenance until reviewed. Import execution history clears; employee master import details remain attached to employees. Attachment references clear while storage objects remain available for recovery.

Only an administrative service-role request identifying an active OWNER can invoke reset. The request requires the owner's complete durable backup, its exact SHA256, an isolated restore receipt already verified against all manifest hashes, and the exact confirmation phrase. Ordinary app sessions cannot export private backups or execute reset. The old reset that deleted SKU masters is revoked; old mounted forms are harmless and the stock screen explains managed, verified reset.

The reset locks public data and auth identities, compares a fresh snapshot to the verified backup, and rejects intervening data/schema changes. It deletes in foreign-key dependency order with no CASCADE or system-trigger disable. User trigger modes are restored in the same transaction. Master fingerprints exclude only derived customer points/spending/tier and recurring posting progress, which are reset explicitly. Account IDs, schema safeguards and all other master values must remain identical. A final failure rolls back all preceding deletion and trigger changes. Repeating a completed backup request returns its original result.

A private retained reset timestamp prevents old recurring/depreciation catch-up. Recurring definitions stay active with current-month progress; explicit skipped reset periods are recognized by the existing caller rather than treated as missing journals. Next-period recurring posting still validates the prior marker and creates one complete journal. Depreciation reads the same boundary before writes; it fails closed when that check is unavailable.

Focused recurring/month-end/depreciation tests passed, including a populated asset producing balanced next-period posting input. TypeScript and scoped lint passed after the recurring caller change; final combined release checks remain required.
