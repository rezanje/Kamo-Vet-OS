# N02 — branch identity on new purchase order numbers

The feedback asks for PO origin to be recognizable from its number. Current PO numbering resolves date tokens only and the atomic creator shares one prefix across branches. Keep existing date/custom-prefix settings and append the authoritative selected branch code plus `-` before sequence digits: e.g. `PO-20261023-TESTA-0001` and `PO-20261023-TESTB-0001`. This placement is an implementation choice under the user's explicit autonomous/main-first instruction, not a claimed user-selected punctuation policy.

Apply in the existing atomic RPC after branch/warehouse/access checks and exact request replay. Lock the active branch row while reading code. Preserve retry receipts, per-prefix advisory numbering locks, unique constraint handling, PO payload/value, role/branch checks and historical document numbers. Blank/unsafe branch codes or expanded numbers over the existing 30-character limit fail clearly; never truncate or invent a code. Branch code edits create a new series for new requests; retries retain the original number. Historical branch identity remains the stored branch FK, not reverse parsing of a mutable code.

Alternatives: client-only suffixing would miss direct RPC callers and race master edits; introducing a global branch-token language would broaden every document type and requires policy for missing context. Choose a bounded server-side PO-only suffix; other document numbering and configured patterns are untouched. UI numbering help/PO example explains the automatic suffix using an explicitly illustrative code.

No data backfill/deletion, new permissions, security changes, financial policy, or unrelated selector work. One guarded additive migration replaces only the existing creator definition and preserves its signature, owner, ACL and authorization. Main-first release requires focused SQL/app tests, basic aggregate checks, review and exact-head deployment verification; full operational UAT remains deferred.
