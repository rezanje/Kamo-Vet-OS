# Mekanisme COA & jurnal — I02, J02, P02, M01 (31 Okt 2026)

Permintaan: "bantu mekanisme COA" (Andri). Titik awal checklist I02, J02, P02, M01 (kolom A–N).
Bukan perombakan master COA. Semua uji memakai data fiktif di PostgreSQL sekali pakai; tidak ada
akses ke database produksi, tidak ada transaksi uji produksi, tidak ada perubahan Sheet.

## 1. Mekanisme saat ini (transaksi → pemetaan akun → jurnal → laporan)

| Lapisan | Lokasi | Catatan |
|---|---|---|
| Master akun | `coa_accounts` (0015, header/detail 0113) | Akun dicari lewat **kode**, bukan id. |
| Daftar kode sistem | `src/lib/coa-sistem.ts` `KODE_SISTEM` | Kode keras yang dipakai program (1101, 1102, 1301, 2101, 2102, 3101, 4101, 5101, 5902, …). Kode tidak bisa diubah, akun sistem tidak bisa dinonaktifkan dari layar COA. |
| Pemetaan kas/bank per metode bayar | `payment_account_map` → `cash_accounts.coa_code`; `unit_posting_cash()` (20261007110000) | Cabang → global → bawaan (Tunai 1101, lainnya 1102). |
| Pemetaan selisih stok | `stock_opname_account()` (20261028150000) | Satu tempat: persediaan 1301, selisih 5902 — dipakai opname, dan sekarang juga penyesuaian. |
| Penulis jurnal di database | `sales_write_journal()` (20261004150000) | Menolak jurnal tidak seimbang dan akun yang tidak ada / nonaktif / akun induk → transaksi batal utuh. |
| Penulis jurnal di aplikasi | `postJournal()` `src/lib/posting.ts` | **Best-effort**: bila akun hilang/induk/error, jurnal **tidak dibuat dan tidak ada error**; transaksi sumber tetap tersimpan. |
| Laporan | Neraca/Laba-Rugi via `getAccountBalances` (`src/lib/ledger.ts`); nilai persediaan historis (`src/lib/inventory-historical.ts`) | Neraca menjumlah semua baris jurnal per kode akun. |

Jalur per item:

- **I02 Stok opname** — `post_opname_atomic` (20261023134000, kebijakan 20261028150000): satu transaksi; lebih
  Dr 1301 / Cr 5902 di harga beli master, kurang Dr 5902 / Cr 1301 di biaya lapisan FIFO; kunci ulang
  (`opname_posting_receipts`). Sudah benar dan sudah live (PR #272).
- **I02 Penyesuaian persediaan** (`/pos/penyesuaian`) — sebelum perbaikan ini: ditulis aplikasi langkah demi
  langkah (dokumen → mutasi stok → `postJournal`). Lihat masalah A.
- **J02 Koreksi metode bayar POS** — `correct_pos_sale_payment` (20261024140000): jurnal balik + jurnal
  pengganti, audit `sale_payment_corrections`, kunci ulang, cek periode & rekonsiliasi bank. Akun kas/bank dari
  `payment_account_map`. Lihat masalah B.
- **P02 Koreksi pembelian** — `correct_purchase_invoice_line` / `correct_purchase_order_line` (20261029150000,
  20261029160000): 1301 = perubahan nilai lapisan, 5101 = selisih atas unit terjual, 1105 PPN, 2101 hutang;
  kunci ulang, OWNER saja. Lihat masalah C dan sisa P02.
- **M01 Impor saldo stok** — `prepare_accurate_initial_stock` → `post_accurate_inventory_accounting`: Dr 1301 /

## 2. Masalah yang terbukti dan perbaikannya (branch `claude/focused-wright-ksmcdd`)

### A. I02 — penyesuaian stok bisa menggeser stok tanpa jurnal (bug teknis)
Bukti: `src/app/(app)/pos/penyesuaian/actions.ts` (versi main) memanggil `stockInAtBuyPrice` /
`issueStockDocument` lalu `postJournal`. `postJournal` diam bila gagal; pemeriksaan jurnal sesudahnya
melempar error, tetapi stok dan dokumen sudah tersimpan. Hasil: kartu stok berubah, 1301 tidak.
Juga: tabel `inventory_adjustments`/`_items` bisa ditulis langsung oleh semua pengguna login (kebijakan
`using (true)`), dan jurnal opname/penyesuaian bisa diubah/dihapus lewat API.

Perbaikan — migrasi `20261031113000_i02_inventory_adjustment_atomic.sql`:
- RPC `post_inventory_adjustment_atomic(request_key, gudang, tanggal, alasan, keterangan, rows)`:
  dokumen + rincian + mutasi stok + jurnal dalam satu transaksi; qty sistem dibaca ulang di bawah kunci stok;
  OWNER/ADMIN aktif + akses cabang + modul POS; tanggal masa depan & periode tutup ditolak; akun dari
  `stock_opname_account()` harus aktif **sebelum** ada tulisan (bila tidak: pesan jelas, tidak ada posting);
  barang tanpa saldo gudang ditolak (dulu dilewati diam-diam); retry kunci sama → bukti lama, isi berbeda → tolak.
- Nilai: lebih = qty × harga beli master (dibulatkan 2 desimal, sama dengan perencana koreksi resmi);
  kurang = biaya lapisan FIFO lewat `issue_stock_document_recorded` (bukti lapisan tetap tersimpan untuk koreksi).
  Akun tidak berubah dari perilaku sejak 12 Agustus (1301/5902).
- Tulis langsung ke `inventory_adjustments`/`_items` lewat API ditutup (baca tetap).
- Jurnal hasil posting opname atomik dan penyesuaian atomik dikunci dari ubah/hapus/tambah baris lewat API
  (`guard_stock_posting_journal`). Koreksi resmi tetap jalan.
- Layar: `actions.ts` memanggil RPC; formulir membawa `request_key`.

### B. J02 — jurnal balik/pengganti koreksi metode bayar bisa dihapus/diubah (bug teknis)
Bukti: `pos_sale_journal_protected` (20261020171202) hanya mengenal source `sale*`. Tes: sebagai OWNER
cabang, `delete from journal_lines where entry_id=<jurnal balik>` **berhasil** sebelum perbaikan
(dibuktikan: suite gagal tanpa migrasi). Akibat: jurnal asli dan pengganti sama-sama hidup → pendapatan,
PPN, kas/bank dobel.

Perbaikan — `20261031114000_j02_payment_correction_journal_guard.sql`: fungsi penanda diperluas ke
`sale-payment-reversal`, `sale-payment-repost`, dan id jurnal di `sale_payment_corrections`. Trigger yang
sudah ada memakai fungsi ini; tidak ada data diubah.

### C. P02 — rincian penerimaan barang bisa ditulis langsung (bug teknis)
Bukti: kebijakan `gr_all`/`gri_all` (0093) mengizinkan INSERT/UPDATE/DELETE bagi siapa pun dengan akses
cabang. Mengubah `qty_terima`/`harga` tidak menyentuh stok, lapisan, maupun jurnal 1301/2102. Tes: update
harga/qty baris penerimaan aktif **berhasil** sebelum perbaikan.

Perbaikan — `20261031115000_p02_goods_receipt_write_lock.sql`: cabut hak tulis langsung
`goods_receipts`/`goods_receipt_items` (pola sama dengan `purchase_invoices`). Semua penulis resmi sudah RPC
SECURITY DEFINER; aplikasi hanya membaca. Ekspektasi pesan error di `supabase/tests/goods_receipt_cancellation.sql`
disesuaikan (sekarang ditolak lebih awal: "permission denied").

### D. M01 — tidak ada rekonsiliasi lapisan stok vs GL 1301 per cabang saat mode FIFO (celah laporan)
Bukti: perbandingan per cabang hanya ada sebagai pengaman aktivasi average (20261024110335) yang memberi satu
error umum; laporan historis hanya untuk mode average.

Perbaikan (baca saja, tanpa migrasi): `/laporan/nilai-persediaan/historis` pada tanggal hari ini dan mode FIFO
menampilkan per cabang: nilai sisa lapisan FIFO, saldo GL 1301, selisih, jumlah baris stok minus (tidak
ditaksir), serta jurnal 1301 tanpa cabang. Tidak ada jurnal penyeimbang. Akses tetap OWNER/FINANCE + modul.

## 4. Sisa cakupan per item

**I02** — teknis jalur posting baru selesai. Sisa: reproduksi keluhan dokumen SO asli (butuh nomor SO, cabang,
tanggal); jurnal lama yang mungkin hilang dari jalur penyesuaian lama perlu dicek dengan laporan M01 di atas;
keputusan finance soal dasar nilai (lihat Q1–Q2). Nilai keluar per baris tetap dibulatkan ke rupiah penuh oleh
fungsi lama `issue_stock_document_recorded`; bila biaya lapisan bersen, selisih < Rp1 per baris antara kartu
stok dan GL (tidak diubah di sini).

**J02** — kunci jurnal selesai. Sisa (keputusan): klinik & penjualan online tanpa jalur koreksi metode; hanya
Tunai↔Transfer; bank mengikuti pemetaan metode (tidak bisa pilih rekening); jurnal koreksi bertanggal hari koreksi;
jejak audit hanya terbaca OWNER. `sale_payments` lama diganti baris baru (riwayat tersimpan sebagai snapshot JSON
di audit). Koreksi memakai kunci tabel jurnal penuh selama berjalan (dampak antrean, bukan salah angka).

**P02** — tulis langsung ditutup. Sisa teknis yang **tidak** dikerjakan karena kode baru milik alur lain
(20261029150000/160000) dan butuh keputusan desain:
1. Edit harga PO (harga faktur sudah benar) menimpa harga/qty penerimaan tanpa jurnal 1301/2102 → pembatalan
   penerimaan/faktur berikutnya bisa macet.
2. Tanggal penerimaan tidak dicek terhadap periode tutup saat penerimaan ditimpa.
3. Pembatalan penjualan setelah koreksi harga mengembalikan unit ke lapisan lama di biaya lama → 5101 lebih,
   1301 kurang sebesar selisih harga × unit batal.
4. Koreksi harga FIFO tanpa jejak di kartu stok.

**M01** — laporan rekonsiliasi posisi hari ini tersedia. Sisa: total kontrol Accurate per cabang (data dari
pengguna), batch PDRY 069e49ba yang terposting tanpa jurnal 1301 (keputusan finance), rekonsiliasi tanggal
lampau di mode FIFO tidak mungkin dari data lapisan. Temuan impor (tidak diubah, area alur impor M04):
pesan error konversi satuan menyebut "pecahan di bawah 0,01" padahal penyebabnya pembagian nilai per satuan
dasar; batch tertentu tidak bisa dibulatkan ("Residu tidak dapat direpresentasikan").

**Prasyarat database** — tiga migrasi baru harus dipasang berurutan **sebelum/berbarengan** dengan kode
(layar penyesuaian memanggil RPC baru). Nomor 20261031113000/114000/115000 tidak bentrok dengan PR terbuka.
Catatan antrean: main sudah punya dua pasang nomor versi kembar (20261029140000 ×2, 20261029150000 ×2) — perlu
diperhatikan pemegang antrean migrasi.

## 5. Temuan lintas modul (di luar empat item, belum dikerjakan)

`postJournal()` (aplikasi) masih best-effort di 14 jalur: pengajuan & penggajian HRIS, pengeluaran klinik,
uang muka penjualan, penjualan online (aplikasi), pembelian aset, sinkron, kas, penyusutan, tutup shift. Bila
akun hilang, transaksi tersimpan tanpa jurnal dan tanpa pesan. Usulan: ubah per jalur menjadi RPC atomik seperti
penyesuaian, atau minimal tampilkan kegagalan. Tidak diubah di sini karena di luar scope.

## 7. Panduan mencoba setelah rilis (tanpa transaksi uji produksi)

1. Owner/Finance buka *Laporan → Nilai persediaan → Valuasi as-of*, tanggal hari ini: tabel "POSISI FIFO HARI INI
   vs GL 1301" muncul per cabang. Catat cabang dengan selisih ≠ 0 untuk ditinjau; jangan buat jurnal penyeimbang.
2. Layar *Penyesuaian Persediaan Baru* terbuka normal (tanpa menyimpan). Penyesuaian nyata berikutnya yang memang
   perlu dilakukan operasional: cek di detail dokumen dan Buku Besar 1301/5902 bahwa satu jurnal terbentuk dengan
   nomor PS yang sama.
3. Koreksi metode bayar POS berikutnya (bila memang ada kasus nyata): jurnal balik/pengganti terlihat di Jurnal;
   tidak perlu mencoba menghapusnya.
4. Penerimaan barang tetap lewat layar terima/koreksi seperti biasa.
